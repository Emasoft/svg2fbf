## 1. Context

The current pipeline is documented in `docs/RELEASE_WORKFLOW.md`:

```
dev      → alpha    (CI disabled, manual testing)
testing  → beta     (CI disabled, manual testing)
review   → rc       (CI enabled)
master   → stable   (CI enabled, publishes to PyPI)
main     (mirror of master)
```

Promotion is via `just promote-to-{testing,review,stable}` (merge with
`--no-ff` + push) and `scripts/release.sh --{alpha,beta,rc,stable}`
(version bump + Docker E2E gate + tag + GitHub release + optional PyPI).

The Docker E2E suite (T1–T13) is the release-blocking gate. It builds a
clean `python:3.12-slim` image with `fonts-dejavu` + `fonts-liberation`
and runs auto-install (T1–T10), the text→path E2E (T11–T13), and the
non-text byte-exact E2E.

## 2. Issues observed during the TRDD-c2a3199d landing

### 2.1 Byte-exact tests were version-pinned (FIXED)

Both byte-exact test sites (`tests/test_e2e_byte_exact.py` and the T12
step in `scripts/test_release_clean.sh`) used naked `cmp` against
goldens that embed the running svg2fbf version twice (in a comment
header and in the `<fbf:generatorVersion>` metadata). Every promotion
across the alpha/beta/rc/stable boundary forced a manual golden regen
on what was a single-line metadata diff.

**Fix already landed:** strip those two lines on both sides before
comparing. Goldens now serve any branch.

### 2.2 Text→path golden was platform-pinned (FIXED)

`tests/fixtures/e2e/text_frames/expected.fbf.svg` is generated by
`svg2fbf --text2path`, which rasterises text via fontconfig + the
system DejaVu Sans font. macOS DejaVu and Linux DejaVu have different
glyph metric tables, so a regen on macOS produces a golden that fails
the Docker T12 byte-exact (Linux DejaVu) test. The previous workflow
left this implicit — anyone regenerating the golden could silently
break the T12 gate.

**Fix already landed:** `scripts/regen_text_frames_golden.sh` always
regenerates this golden inside a Docker container that mirrors the
T13 image. The script is the documented and only entry point.

### 2.3 Docker output drifted between runs (PARTIAL FIX)

Across two Docker E2E runs on the same dev branch a few hours apart,
the produced FBF differed at `<path d="…">` glyph coordinates. Both
runs used `apt-get install fonts-dejavu` and a fresh image build, but
something between them changed — most plausibly:

1. svg-text2path / svg-bbox auto-installed a newer npm tag.
2. `apt-get update` pulled a newer fonts-dejavu.
3. Layer-cache vs no-layer-cache build path resolved slightly different
   font files.

The fix in 2.2 absorbs this for the immediate regression — the golden
is just regenerated to whatever the current Docker output is — but
the underlying non-determinism is still there. **Not fully fixed.**

## 3. Proposed pipeline improvements

### 3.1 Pin the apt + npm dependencies that drive byte-exact output

For the T11/T12 lane to be reliably reproducible across machines, days,
and CI runners, pin:

- **fonts-dejavu** to a specific Debian package version (e.g. `fonts-dejavu=2.37-8`) rather than just `fonts-dejavu`.
- **svg-text2path / svg-bbox** to specific npm versions, ideally vendored or pinned via a top-level `package.json` rather than auto-install-on-first-run.
- **bun** to a specific release.

This eliminates the entire class of bug from §2.3 above and lets the
text→path golden survive months without a regen.

Trade-off: pinning means we don't pick up upstream font/text-shaping
fixes automatically. That's actually desirable for a deterministic
test gate.

### 3.2 Cache the Docker image base layer

`scripts/test_release_clean.sh` rebuilds the entire image every run
(~10 min on Apple Silicon). The `apt-get install` of fonts + chromium
is the slow part and rarely changes.

Proposed: split the Dockerfile into two stages. The **base** stage
(python + apt deps + fonts) is built once and tagged `svg2fbf-test-base:<digest>`.
The **wheel** stage `FROM svg2fbf-test-base:<digest>` only adds the
wheel + entrypoint. Use BuildKit `--cache-from` so CI runs hit the
cache.

Expected savings: 8–9 min per run.

### 3.3 Selective test runs

Add a `--tests T11,T12,T13` filter to `test_release_clean.sh`. When
iterating on text→path code, running just the text lane (~2 min after
image cache) is much more ergonomic than the full T1–T13 (~10 min).

### 3.4 Promotion ergonomics

`just promote-to-testing` currently does merge + push with no Docker
E2E gate. If the merge introduces drift, the failure surfaces only
when someone runs `release.sh --beta testing`.

Proposed: insert `test_release_clean.sh --docker-only` between the
merge and the push in `promote-to-{testing,review,stable}`. If the
merge breaks Docker E2E, fail before pushing.

This is essentially "treat promotion as a release rehearsal".

### 3.5 CI on testing branch

The current rationale for "CI disabled on dev/testing" — *expected
breakage during active development* — makes sense for unit tests but
not for the Docker E2E gate. The latter doesn't fail because of
in-progress feature work; it fails because of regressions in deps,
fonts, or output format.

Proposed: enable a single GitHub Actions workflow on `testing` that
runs `test_release_clean.sh --docker-only`. Keep host pytest CI
disabled there (where the "expected to fail" rationale does apply).

### 3.6 Replace `cmp` with a structured diff helper *(downgraded — keep duplicated)*

The `cmp file1 file2 || diff … | head -10` pattern is duplicated three
times in `test_release_clean.sh` (now four with the version-strip).
Originally proposed extracting into a shell helper, but
`~/.claude/CLAUDE.md` ("Don't Over-Engineer") and the project's own
"Three similar lines is better than a premature abstraction" guidance
both argue against this. Each `bash -c '…'` block runs in its own
process and can't share an in-memory function anyway, so the extraction
would mean shipping a separate `_compare_byte_exact_stripped.sh` into
the Docker image at COPY time — more file-management overhead than the
duplication it removes. **Decision: keep the three copies.** Revisit
only if the strip pattern needs to grow beyond the two lines it
already covers.

### 3.7 Single-source release configuration *(downgraded — keep duplicated)*

`scripts/release.sh` and `scripts/test_release_clean.sh` both encode
"the deps the wheel needs to bootstrap". Today they only mostly agree —
the regen script `scripts/regen_text_frames_golden.sh` had to copy the
relevant snippets. A small `scripts/lib/docker_image.sh` module that
emits the Dockerfile fragment would let all three scripts use the
same base. Same trade-off as 3.6: the common base is ~5 lines, and a
sourcable Bash helper that emits them adds an indirection (and a load-
order dependency between scripts) that costs more than it saves.
**Decision: keep the duplication.** Revisit only when a third or
fourth consumer of the same fragment appears.

## 4. Priority order

1. **3.1 (pin deps)** — directly fixes §2.3, biggest win for trust in the gate.
2. **3.2 (cache base)** — biggest dev-loop win.
3. **3.4 (promotion gate)** — catches regressions before they hit `release.sh`.
4. **3.5 (CI on testing)** — needs decision on workflow file ownership.
5. **3.3 (selective tests)** — nice-to-have.
   *(3.6 and 3.7 were downgraded out of the priority list — see their
   entries above for the rationale.)*

## 5. Open questions

- Are upstream dependency updates (fonts, svg-text2path) something we
  *want* to track via tests breaking? Some teams use deliberate test
  failures as upgrade signals. If so, §3.1 should pin only fonts and
  let svg-text2path float, with a separate canary test.
- Is the Apple-Silicon-vs-x86 fork in the Dockerfile (system chromium
  vs Puppeteer's bundle) sustainable, or should the dev loop just use
  x86-emulation always? The arch fork is a regular source of "works on
  one machine, fails on another" reports.

## 6. Non-goals

- This TRDD is **not** proposing changes to the four-branch model
  (`dev → testing → review → master`) itself. That model is well-
  established and has its own cadence.
- This TRDD is **not** proposing CI for `dev` — see §3.5.
- This TRDD is **not** proposing to reduce or relax the byte-exact
  test discipline — version-stripping is purely about ignoring
  metadata, not about loosening wire-format policing.
